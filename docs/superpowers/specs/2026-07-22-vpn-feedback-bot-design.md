# Telegram-бот обратной связи для VPN-сервиса — дизайн

## Контекст и цель

VPN-сервис на базе Marzban (либо совместимого форка с REST API), ~22 пользователя. Сейчас нет канала для фиксации проблем — пользователи не жалуются, хотя сбои могут быть. Нужен Telegram-бот, который:

1. Принимает и фиксирует жалобы на работу VPN.
2. Напоминает пользователям о продлении подписки на основе даты, которую администратор проставляет в панели Marzban.
3. Даёт пользователям самостоятельный доступ к статусу своего аккаунта и инструкциям по подключению.
4. Позволяет администратору рассылать объявления всем пользователям разом.

Администратор — один человек (владелец сервиса), полный контроль над привязкой аккаунтов и рассылками.

## Стек и архитектура

- **Python 3.12 + aiogram 3** — основной фреймворк бота, polling-режим (вебхук не нужен при таком масштабе, не требует белого IP/сертификата).
- **SQLite** (через `aiosqlite`) — вся требуемая история и статистика умещаются без отдельной СУБД.
- **APScheduler** — фоновая ежедневная задача проверки дат истечения подписки.
- Отдельный модуль-клиент Marzban REST API: получение токена администратора, чтение данных пользователя (трафик, дата истечения, статус активности) по логину в панели.
- Конфигурация — через `.env` (токен бота, Telegram ID администратора, адрес и креды Marzban API, порог напоминания в днях).

## Деплой

- Ubuntu-сервер, отдельный от машины разработки.
- **Docker + docker-compose**: один контейнер с ботом, volume для SQLite-файла и для `.env`. Обновление — `git pull && docker compose up -d --build`.
- Код хранится в GitHub-репозитории `melekhov-sa/obrSvaz`.

## Модель данных

```
users
  telegram_id     PK
  username
  first_name
  marzban_login   NULL, пока не привязан через токен-ссылку
  linked_at

complaints
  id              PK
  telegram_id     FK -> users
  text
  created_at

reminders_sent
  telegram_id
  sent_for_date   # дата истечения, под которую уже отправлено напоминание
  # уникальность по (telegram_id, sent_for_date) — не дублировать напоминание

link_tokens
  token           PK   # например LNK_ + 8 случайных символов
  marzban_login
  created_at
  used_at         NULL пока не использован
  used_by         NULL -> telegram_id после использования
```

## Команды и сценарии

### Привязка аккаунта (через токен-ссылку)

- **`/genlink <marzban_login>`** (только админ) — генерирует уникальный одноразовый токен, привязанный к указанному логину в панели, и присылает готовую ссылку `t.me/<bot>?start=LNK_xxxxxxxx`. Администратор пересылает её конкретному пользователю любым каналом (не обязательно через сам бот).
- Пользователь переходит по ссылке → бот получает `/start LNK_xxxxxxxx` → проверяет токен:
  - если валиден и не использован — сохраняет `telegram_id ↔ marzban_login` в `users`, помечает токен использованным (`used_at`, `used_by`), подтверждает пользователю успешную привязку;
  - если токен уже использован или не существует — сообщает об ошибке и просит обратиться к администратору за новой ссылкой.
- Токен бессрочный (не протухает по времени), но одноразовый.
- Если для логина, у которого уже есть активная привязка, администратор генерирует новый токен и его использует другой (или тот же) `telegram_id` — новая привязка замещает старую: у прежнего `telegram_id` поле `marzban_login` очищается, у нового — устанавливается. Так поддерживается переезд пользователя на новый Telegram-аккаунт или перевыпуск потерянной ссылки без ручной зачистки БД.
- Неиспользованные токены, сгенерированные ранее для того же логина, остаются формально валидными до первого использования — на практике это не проблема, т.к. ссылка отправляется одному конкретному человеку.
- **`/start`** без параметра — обычная регистрация в `users` без привязки логина. Доступны жалобы и FAQ; `/status` сообщает, что нужно дождаться привязки от администратора.

### Жалобы

- **`/complain`** — бот просит одним сообщением описать проблему → сохраняет запись в `complaints` → пересылает администратору в личку (кто пожаловался, когда, текст) → подтверждает пользователю номер обращения.

### Статус

- **`/status`** — если `marzban_login` привязан, бот запрашивает Marzban API и показывает: использованный трафик, дату окончания подписки, активен ли профиль. Если не привязан — просит дождаться привязки.

### FAQ и инструкции

- Статический раздел с инлайн-кнопками по платформам (iOS/Android/Windows/macOS/роутер) + частые проблемы подключения. Контент задаётся в коде/конфиге, правится напрямую в репозитории.

### Рассылка объявлений

- **`/broadcast <текст>`** (только админ) — рассылает сообщение всем зарегистрированным пользователям из `users`. По завершении присылает администратору отчёт: скольким доставлено, скольким не удалось (например, пользователь заблокировал бота).

### Статистика по жалобам

- **`/stats`** (только админ) — сводка по `complaints`: всего, за последнюю неделю, разбивка по пользователям.

## Напоминания о продлении

Ежедневная задача (например, в 10:00 по серверному времени):

1. Для каждого пользователя с привязанным `marzban_login` запросить дату истечения через Marzban API.
2. Если до истечения осталось ≤ N дней (порог из `.env`, по умолчанию 3) и напоминание под эту дату ещё не отправлялось (проверка по `reminders_sent`) — отправить пользователю напоминание и записать факт отправки.
3. Дату истечения администратор проставляет сам в панели Marzban — бот только читает её и напоминает, никакого биллинга или автопродления бот не делает.

## Обработка ошибок

- Marzban API недоступен: `/status` и джоба напоминаний логируют ошибку и мягко информируют («не удалось получить статус, попробуйте позже» пользователю; джоба просто пропускает цикл без падения).
- Незарегистрированный/непривязанный пользователь получает понятные подсказки вместо технических ошибок.
- Невалидный/использованный токен при `/start` — понятное сообщение с просьбой запросить новую ссылку у администратора.
- `/broadcast` устойчив к отдельным сбоям доставки (заблокировавшие бота пользователи не прерывают рассылку остальным).

## Тестирование

- Юнит-тесты — слой работы с БД (репозитории для `users`, `complaints`, `link_tokens`, `reminders_sent`) и Marzban-клиент (с моками HTTP-ответов).
- Ручная проверка основных сценариев перед вводом в эксплуатацию:
  - `/genlink` → переход по ссылке → успешная привязка → повторный переход по той же ссылке даёт ошибку;
  - `/complain` → жалоба доходит администратору и видна в `/stats`;
  - `/status` для привязанного и непривязанного пользователя;
  - напоминание срабатывает за N дней до даты из панели и не дублируется при повторном запуске джобы в тот же день;
  - `/broadcast` доходит всем, отчёт корректно считает недоставленные.

## Вне рамок (сознательно не делаем)

- Выдача/перевыпуск конфигов через бота — распространяется вручную.
- Оплата/биллинг через бота — только напоминание, продление вне бота.
- Автодиагностика (пинг ноды и т.п.) при жалобе — жалоба просто фиксируется как есть.
